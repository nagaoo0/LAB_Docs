Steering an entity along the scene's navmesh, and reading or injecting into a behaviour tree that is already running. See [Lua Scripting](../../index.md) for how a script runs and when its callbacks fire.

Two separate things share this corner of the API. A **nav agent** is an entity with a `NavAgentComponent` walking to destinations across the baked navmesh. An **AI controller** is an entity with an `AIControllerComponent` evaluating a behaviour tree. The `move_to` family steers the first, and the `ai_*` family inspects the second.

[C++ equivalent](../../../03-cpp/api/ai/01-navmesh-and-behaviour-trees.md)

The navigation half needs a **baked navmesh**: one `NavMeshVolumeComponent` in the scene whose baked asset has been produced (the editor's Bake Navmesh button, or `scene.bake_navmesh(volume)` from a script). The scene loads it once play starts. A scene with none is a scene where `move_to` answers `false` and nothing moves.

## `move_to(target)`

```lua
if not entity:move_to(vec3.new(12, 4, 0)) then
    log.warn("no path to the patrol point")
end
```

Plans a corridor across the scene's baked navmesh and starts following it. Answers `true` when a path was found and the agent is moving, `false` when there is no loaded navmesh or no path exists, and `false` for an entity that does not exist.

**It plans and follows; it does not move anything on the spot.** An agent's movement happens in the scene's own update, once per frame, before the physics step, so this call sets a destination and returns long before the entity goes anywhere. That is why it answers "was a path found" rather than "did it arrive", and why there is a separate call to ask about arrival.

**An entity with no `NavAgentComponent` gets one, with its defaults**: radius 0.4, height 1.8, speed 3.5 metres per second, acceleration 8 metres per second squared, and a stopping distance of 0.15. So a script can steer something that was never authored as an agent.

Both the agent's own position and the target are snapped to the nearest navmesh polygon, generously on the vertical axis, so a destination slightly off the mesh or floating above a floor still works. A destination no polygon is near answers `false`, and so does one on ground the agent cannot reach from where it stands, such as a floor joined to this one only by a one-way link pointing the other way. (Before 2026-10-02 such a move walked to the nearest reachable edge and then reported itself arrived.)

An agent paired with a **`CharacterControllerComponent`** is steered through it: the scene sets the controller's move velocity in its own nav update and the physics step that follows consumes it, so the agent is pushed through collision rather than dragged through it. An agent without one has its transform advanced directly. Either way the steering is **horizontal**: only x and y are driven, so rising ground does not carry the agent up a slope on its own.

A call from `on_update` steers from the next frame on, since the nav update has already run for the frame the script is in.

## `is_move_complete()`

`true` when the agent is walking nowhere: idle, arrived, failed, or not an agent at all. `false` while it is following a path.

```lua
if entity:is_move_complete() then
    log.info("idle or arrived")
end
```

An entity with no `NavAgentComponent` also answers `true`, which is the answer this facade gives for anything it cannot resolve. So "the agent arrived" and "there is no agent" are the same observation, and a script that needs to tell them apart should keep its own flag from `move_to`'s answer.

## `is_on_nav_link()`

`true` while the agent is crossing a [Nav Link](../../../../04-gameplay/03-navigation-and-ai.md#nav-links): from the moment it leaves the link's start until it lands at the other end. `false` otherwise, and for an entity with no agent.

```lua
local wasJumping = false
function on_update(dt)
    local jumping = entity:is_on_nav_link()
    if jumping and not wasJumping then
        entity:set_anim_parameter("Jump", 1)
    end
    wasJumping = jumping
end
```

A crossing always finishes. A `move_to` or `stop_moving` during one takes effect when the agent lands, and `move_to` then plans from where the link lands rather than from the air.

## `stop_moving()`

Cancels the current path. The agent stays where it is, and `is_move_complete` then answers `true`. No-op for an entity with no agent.

A character-controller agent also has its move velocity zeroed, so it stops on the step that follows rather than coasting one more frame.

```lua
entity:stop_moving()
if not entity:move_to(threat) then
    log.warn("threat unreachable")
end
```

## `ai_current_state()`

The name of the state a running behaviour tree is in, or `''`.

`''` is also the answer for an entity with no `AIControllerComponent`, a tree that has not started, and a tree that has no current state. So "not an AI" and "no state yet" are indistinguishable here, and a script checking this compares the string against the names it expects.

This is the read side of a behaviour tree, for a script that wants to react to what the AI decided: play a sound on `"Attack"`, change a HUD icon on `"Alert"`.

There is **no scripting API to author a behaviour tree**. States, tasks and transitions are authored in the scene file or a `.Lbehavior` asset, the same way an animation graph is authored in a `.Lanimgraph`; a script only inspects and injects into one that is running.

## `ai_get_blackboard(name)` / `ai_set_blackboard(name, value)`

```lua
entity:ai_set_blackboard("PlayerVisible", 1)

if entity:ai_get_blackboard("Alert") > 0 then
    log.info("the tree noticed")
end
```

Reads and writes a behaviour tree's named parameters: **live-value injection, not authoring**. The tree's states, tasks and transitions stay exactly as loaded. This is the same write a Set Blackboard Value task already does from inside the tree, now reachable from a perception or sensing script outside it.

`ai_get_blackboard` answers `0` for an entity with no `AIControllerComponent`, and for a name the tree does not have. `ai_set_blackboard` answers `false` in those same cases and `true` when the value landed, so a typo is inert rather than an error. That is the same tolerance a mistyped input action name gets.

The value written is a number, so a bool parameter reads `1` and `0`. A tree task **bound** to a blackboard parameter re-reads it fresh on every tick rather than freezing at whatever it held when the field was authored, so a value written here is picked up on the next tick with no wiring.

## A navmesh has to exist before the first tick

Worth knowing when a tree looks like it is skipping its movement state.

An `AIControllerComponent`'s entry state starts evaluating on the very first frame, before that frame's own `on_update` has run. A Move To task in the entry state therefore asks for a path on frame one.

A scene that bakes its navmesh from a script's `on_update` finds no navmesh loaded yet. The task fails immediately, and a transition gated on "the state's tasks are complete" does not distinguish succeeded from failed, so the tree moves straight past the state that never got to run. The symptom is an agent that never moves and a tree that looks like it worked.

The fix is to have the navmesh baked and loaded before play starts: point the volume at a baked file, or bake from `on_create`, which runs before frame one.

## What is not here

There is no navmesh query beyond `move_to`: no raycast against the navmesh, no "find the nearest point on it", and no way to ask about the path a `move_to` planned. An agent's own fields (speed, acceleration, stopping distance, radius) are authored on `NavAgentComponent` in the Properties panel and are not writable from a script.

For behaviour trees, there is no way to create or edit one from a script, only to read its current state and inject blackboard values into it.
